Part 1

What is a decision model?

And where did it come from?

Definition

A question with a fixed list of answers, and a probability for each

StateA message, a clause, a log, an agent's next action
+
QuestionA fixed list of options, each with a description
→
OutOne probability per option. No free text.
TypeAsksReturns

noul / predicateIs it true?P(true)
STATE (illustrative, BANKING77-style)

"I was charged twice for the same coffee this morning."

QUESTION: which intent?
charged_twice.81
wrong_amount.09
pending_payment.06
request_refund.04

Software branches on the numbers: act, double-check, or escalate.

Three ingredients: the state, the question with its options, and a probability per option back.

Three question types. The names come from TypeSafe's API (noul); OpenAI calls the yes/no one "predicate". The limits (255 options, 10 levels) come up again later as a fingerprint.

Definition

Same model family, different output: don't talk, decide

Using a chat LLM

State + options in a prompt
Generate tokens: reasoning, then an answer
Parse text / JSON, handle invented labels
One answer, usually no usable probability

Using a decision model

State + options in a structured request
One pass; nothing is generated
Always a valid option, never a parse error
A probability per option you can put a threshold on
Bounded output removes invalid answers. It does not remove wrong answers: a decision model can be perfectly valid and confidently wrong.

The core contrast. A chat model has to talk its way to an answer; a decision model is asked to put probability mass on options you gave it.

In our own runs, GPT-OSS generating answers invented 30 labels on BANKING77. A decision model can't do that. But "can't hallucinate a label" is not "can't be wrong".

Where they came from

Not a new idea: zero-shot like an LLM, output like a classifier

Before 2018
Trained classifiers
Probabilities per class, fast and cheap. One model per task, thousands of labels needed.
2018–19
Fine-tuned BERT, zero-shot via NLI
Fewer labels; "does this text entail label X?" as a zero-shot trick.
2020–21
Prompted LLMs, label scoring
Read the likelihood of each label. Works, but biased by format and order.
2023–25
Chat LLMs + JSON outputs
Great zero-shot judgement; text out, no reliable probability. Reasoning models hide logprobs.
Sep 2026
Decision models
LLM-level zero-shot judgement, classifier-style output, as a product.
The new part is the packaging: you get an LLM's zero-shot judgement with a classifier's output, behind a single API call.

We've had probability-per-class models forever; they needed labelled data per task. LLMs removed the need for labels but moved us to text.

Decision models try to get both. Keep the 2021 "calibrate before use" lesson in mind: reading label probabilities from an LLM is biased by format and order. That shows up again in our results.

Side note: GPT-6 Luna, as a reasoning model, rejects logprob requests, so you can't get these probabilities from it yourself (our experiment A3).

"System One"

The name echoes Kahneman's fast, intuitive System 1. TypeSafe's thesis: LLMs were optimised to talk, but software needs values it can branch on.

Same programming model

All three share the same idea: one state, several typed questions, a probability per option. The question types and API limits are almost identical.

This went from one start-up to a category in under four weeks.

TypeSafe was co-founded by Diogo Almeida, previously at OpenAI; the pitch was that language generation is the wrong primitive for automation.

The resemblance across the three APIs is what made us ask whether they share a mechanism. We could only test Decision-1.

Part 2

Why do they matter?

Speed, cost, and a probability you can build a policy on.

Why it matters

Three properties that a chat LLM doesn't give you by default

~0.5 s
per decision, flat from 2 to 77 options (Decision-1, our measurement). Nothing is generated.

Microsoft's framing: 100 ms extra on each of 20 chained decisions is 2 s per workflow.

$0.03
per 1,000 decisions (Decision-1 on our benchmarks)

vs. $0.08–0.28 per 1,000 for GPT-6 Luna on the same tasks: 2.4–7.7× cheaper.

P(x)
a probability per option, not just an answer

If it is calibrated, "90% sure" means right 9 times in 10, and you can automate above a threshold.

The third one is the real product. Accuracy tells you if the model is right; calibration tells you if you can build policy on its confidence.

Speed: latency barely changes with the number of options. That's one of the clues to how it works, later.

Cost: per-decision numbers from our runs. Microsoft charges for input tokens only; output is free.

The probability is what makes it more than a fast classifier.

Why it matters

The probability is the product: automate, check, or escalate

p ≥ 0.95 → automateAct directly.
0.70–0.95 → checkStronger model, extra rules, sampling.
p < 0.70 → escalateHuman review.

Applications

Most enterprise "AI judgement" is a bounded decision

Routing & triage

Which queue, team, intent or model should handle this? Our BANKING77 benchmark is exactly this.

Labelling at scale

Xbox Research sorted 10k+ reviews into fixed themes: ~GPT-6 Sol quality, 14× faster, 200× cheaper.*

Compliance & verification

Is this scenario compliant with these clauses? Our ACE benchmark is exactly this.

Guardrails & agent control

Should this agent action be allowed? Is this a prompt injection? Harmful or harmless?

Evaluation & grading

Rubric scores for LLM answers and agent steps. The Copilot team tested it for response-quality checks.*

Workflow control

Is this evidence sufficient? Is the task done? Replan or continue? Many small decisions in a loop.

* Microsoft's own reported internal results (Command Line blog, 9 Oct 2026), not verified by us.

The common pattern: unstructured state in, small fixed answer space out, and the decision feeds software.

Agents are the big one: an agent makes dozens of small control decisions; each one being 0.5 s and cheap matters more than each one being eloquent.

Applications

…and when you should reach for something else

Good fit

  • "At a glance" judgement over a fixed answer space
  • Many options (tens to hundreds of intents)
  • No labelled data yet, or the labels change often
  • High volume, latency-sensitive, chained decisions
  • You need a confidence to drive automate-or-escalate

Think twice

  • You have a few thousand labels: embeddings + logistic regression hit 0.944 on BANKING77 at $0.002 per 1k
  • The decision needs deliberation: one-pass readouts collapse on compliance reasoning (later)
  • Numbers, multi-step indirection: Jev's own docs flag these
  • Open-ended output: it can only pick from your list

The honest counterweight: with labelled data, a classifier on embeddings beat every zero-shot method we tried on BANKING77, at a fraction of the price.

Decision models shine when you don't have labels, the label set changes, or you need many different questions without training a model for each.

Part 3

What we found

How does Microsoft-Decision-1 work, and can we rebuild it from open parts?

Our study

Four ways of looking at one black box

1. Benchmark

Decision-1 vs. GPT-6 Luna vs. embeddings on accuracy, calibration, latency, cost.

2. Probe

~2,000 deliberately altered API requests. Forensics on returned numbers and billed tokens.

3. Compare

Run its open base, Qwen3.5-9B, the same way. Compare decision by decision.

4. Rebuild

Fine-tune Qwen3.5-9B with LoRA to see which behaviours we can reproduce.

Datasets

  • ACE: is a scenario compliant with contract clauses? 3 options
  • BANKING77: which of 77 intents is this customer message?
  • Never tuned on: MInDS-14, ATIS (intents), ContractNLI (contracts)

Plus a side experiment

On open gpt-oss-20b, we kept the weights fixed and changed only the readout, i.e. how the decision is pulled out of the model: generate, score labels, read one token, or train a small head.

We had no access to internals, so everything is black-box: what goes in, what comes out, what gets billed.

The base-model comparison is the strongest tool: same weights before post-training, so differences point at training or serving.

How the answer is computed

It never writes a word: one score per option, then a plain softmax

Billed exactly one output token per question

Even when option names are long. Nothing is generated.

A bf16 fingerprint in the probabilities

In 99.8% of answers, the gaps between returned log-probabilities are exact multiples of a bf16 rounding step, the 16-bit format the model computes in. Any post-processing (temperature, averaging over orders, scoring in groups) would erase it. It holds up to 255 options, so all options are scored in one go.

So calibration lives in the weights

Nothing touches the numbers after the softmax. Whatever calibration it has must come from training.

The confidence field

(pmax − 1/K)
÷ (1 − 1/K)

K = number of options. 0 = uniform, 1 = certain.

This is exactly the formula TypeSafe documents for Jev.

The bf16 trick is the most fun finding. Log-probabilities from a softmax are logit minus a constant, so gaps between them are gaps between logits. Logits computed in bf16 sit on a coarse grid, so the gaps land on grid multiples. Post-processing would knock them off the grid.

That rules out a separate calibration step. It doesn't tell us how the training was done.

  • Options are sorted byte-wise by name before the model sees them: uppercase first, then lowercase. The description doesn't affect the order.
  • Asked "which option is listed first / second / last?", it answered by sorted order in 48 of 48 requests.

Why it matters

Microsoft's "zero flips when options are reordered" is true, but the robustness comes from the serving code, not from the model.

Practical consequence

The option name decides the position the model sees. Renaming an option can move it, and position effects come back.

Robustness you get for free, as long as you know it comes from the serving code.

We just asked it. "Which option is listed first?" and it named the alphabetically first one every time, regardless of what we sent first.

LLMs are known to be sensitive to option order. Sorting makes the input canonical, so reordering can't change anything. Nice engineering, but not a property of the model.

How the input is handled

Options are judged together; the state is read once

Options are scored jointly

The score gap between two options changes when other options are added. They are not scored one by one.

Questions share the state

State billed once; each extra question adds only its own tokens. The same question asked twice in one request gets bit-identical answers.

A tiny hidden prompt

Qwen3.5 tokenizer, with only ~21 tokens of hidden template. It was trained on a compact format, not steered by long instructions.

Descriptions are read in full

Tested up to ~1,650 tokens per option; facts at the very end were still used.

Mental model: one shared state, then each question with all its options in view at once.

The billing data gives a lot away. We can count exactly how many tokens each part of the request costs.

21 hidden tokens is very short: think "a short delimiter plus a format the model was trained on", not a long system prompt.

Routing: trust it

BANKING77 needs no correction (ECE 0.015). Training fixed the base's overconfidence (1.41 → 1.02). Unseen intent sets are slightly underconfident (T fitted on the reported items).

Compliance: recalibrate first

Overconfident on contract tasks. On ACE the base ranges 0.64–2.51 depending only on prompt layout, so no calibration gain from training there.

Temperature scaling: divide log-probs by T and re-softmax. It never changes the winner, only how confident it is.

Practical: on routing-like tasks you can threshold its numbers directly. On compliance-like tasks, fit a T on your own labelled data first.

Side experiment · same gpt-oss-20b weights, different readouts

How you read the model matters as much as the model

Intuitive decisions: one pass is enough

BANKING77: reading the option letter from one forward pass (116 ms) is within 1.5 points of generating with reasoning (949 ms), with better confidence ranking.

Deliberative decisions: think first

ACE: one-pass readouts score 0.45–0.62, vs. 0.69–0.77 when the model reasons first. Reason, then read the probabilities, gives the best of both.

The answer is already inside

A linear head on frozen hidden states scores 0.937 on ACE and 0.903 on BANKING77 (supervised). After only 16–20 of 24 layers: 69–93 ms.

Same weights, different readout, different opinion: on ACE one readout says Not-Applicable 73% of the time, another says Non-Compliant 87% of the time.

This connects back to "System One": fast single-pass judgement works for intuitive tasks like intent routing, not for tasks that need deliberation.

Interesting that Decision-1 still does OK on ACE in one pass (0.741). Our untrained base does too with the right layout. gpt-oss-20b is a reasoning model and seems to rely on its thinking more.

Can it be rebuilt from open parts?

Mostly yes, except the part training adds

The interface: yes

Sort the options, score them all in one forward pass of the open base, compute the state once for many questions. No training needed. We served 64 questions in ~0.85 s on one A100.

Contract reasoning: yes

The untrained base already matches Decision-1; our LoRA fine-tunes match or beat it on ACE and ContractNLI (small margin, 201 items).

Many options: no

Our fine-tunes stay 12–14 points below on BANKING77 and several points below on unseen intent sets.

What didn't close the many-options gap (one run each, judged against 4-run noise)

More and broader real routing data · BANKING77-domain data · 43,000 synthetic messages from 199 domains · 5× longer training · RL with an accuracy reward. Not yet tried: much larger scale, full fine-tuning, distillation, an RL reward for calibration.

The interface and most of the judgement are reproducible on open weights. The many-options skill is the moat. We don't know how it was trained.

Jev's docs say "RL for calibrated decisions"; we tried RL with an accuracy reward, not a calibration reward. That's the next thing to try.

Findings · tier 3 of 3

Assumptions & unknowns

Not testable from outside. Treat as hypotheses.

What we can't see

Open questions about Decision-1

How was it trained?

Fine-tuning, reinforcement learning or distillation, and on what data. Above all: what produces the many-options gain we couldn't reproduce?

The exact labels and template

We know the size (~21 hidden tokens, ~2 per option), not the content.

Was BANKING77 in its training data?

Possible; Microsoft hasn't published its list. The gains on unseen sets show it can't be the whole story.

Logits or a classifier head?

The score sizes fit next-token logits. A dedicated head would look much the same from outside.

These are the things we'd need inside access, or much more compute, to answer.

The training question is the one that matters commercially: it's the only part we couldn't rebuild.

Across the three products

Do Jev and OpenAI Decisions work the same way?

Points of contact with Jev

  • Same API limits and the same confidence formula (confirmed)
  • Jev's docs: reads the state once, answers questions in parallel, leans slightly to the first option. In sorted order, Decision-1 also leans slightly to the first option
  • Jev is "trained with RL for calibrated decisions"; Decision-1's training is unpublished

OpenAI Decisions v1

Reportedly built in about a week on existing GPT-6 Luna weights. If true, a decision API doesn't need a new model, just a different readout and serving. We couldn't test it: Azure returns 404.

Our bet on the common recipe

  1. A strong LLM base
  2. A one-pass readout of one score per option
  3. Serving tricks: canonical option order, shared state for many questions
  4. Post-training aimed at many-option choice and calibration

Shared interface ≠ shared mechanism. This is an assumption.

The honest answer is: we don't know. The API overlap is real but says nothing about weights.

The OpenAI "built in a week on Luna" story is reported, not verified by us. It supports the idea that steps 1–3 are cheap and step 4 is where the differentiation is.

Part 4

So what?

Takeaways

What I'd tell a team about to use one

1. Use it for fast, bounded judgement

Routing, labelling, guardrails, grading. Strongest with many options and no labels.

2. Always write option descriptions

+12 points on ACE. They are read in full.

3. Recalibrate before thresholding

Trust it on routing (T ≈ 1). On compliance-style tasks, fit T on your own labels (we saw 1.6–2.75).

4. Mind the names

Options are sorted by name, so names set the position the model sees.

5. Have labels? Try a classifier first

Embeddings + logistic regression: 0.944 on BANKING77 at $0.002 per 1k.

6. Deliberative task? Reason, then read

One pass is great for intuition, weak for multi-step reasoning.

Six practical rules. If people remember only two: write descriptions, and check calibration on your own data before you automate on it.

One sentence

A decision model is an LLM that isn't allowed to talk.

One forward pass, one score per option, and training that makes the probabilities mean something. Most of it you can rebuild on an open model; the many-options skill is the part you can't (yet).
