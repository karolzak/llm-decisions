"System One"

The name echoes Kahneman's fast, intuitive System 1. TypeSafe's thesis: LLMs were optimised to talk, but software needs values it can branch on.

Same programming model

All three share the same idea: one state, several typed questions, a probability per option. The question types and API limits are almost identical.

This went from one start-up to a category in under four weeks.

TypeSafe was co-founded by Diogo Almeida, previously at OpenAI; the pitch was that language generation is the wrong primitive for automation.

The resemblance across the three APIs is what made us ask whether they share a mechanism. We could only test Decision-1.

What works

  • Strong judgement out of the box, no training
  • A valid, parseable answer every time

What's missing

  • Slow and costly: a pass per piece, plus the thinking. GPT-6 Luna took 1.1–2.7 s per decision on our tasks.
  • No real probability: 0.95 is text the model wrote, not a measurement. Without it, every answer looks 100% sure.
Decision models keep the judgement and skip the writing.

This is how most of us build "AI decisions" today: prompt with the options, let the model write a JSON answer (reasoning models think first), use structured outputs so the JSON is always valid, then parse it.

It works, but you pay for every piece written, and the only "confidence" you get is a number the model made up as text. When the model writes "charged", it has in fact weighed all the options internally; you just only see the one it wrote. That's the hook for the next slide.

One pass, nothing written: instead of the one word the model picked, you get how likely every option is.

Same example as the definition slide. Step 1: options are sorted by name and each gets a short label; the labels here are made up. Step 2: one forward pass; read the next-token scores only at the label tokens. Step 3: softmax over those scores, mapped back to option names.

The labels: green = we measured it (sorting, one output token billed, softmax with no post-processing). Orange = our best explanation that fits all the evidence but can't be proven from outside (the label tokens, reading next-token scores). The same labels appear in the footer of the following slides.

The numbers are illustrative but consistent: softmax of 24.0 / 21.4 / 21.0 / 21.8 gives .81 / .06 / .04 / .09. Confidence = (0.81 − 1/4) / (1 − 1/4) = 0.75.

How it works · the evidence

Four things we measured

1. It never writes a word

One output token billed per question. In 99.8% of answers, gaps between returned log-probs sit on the bf16 grid, so it's a plain softmax with no post-processing.

2. "Order robust" is a sort

Options are sorted byte-wise by name before the model sees them (48 of 48 checks). Reordering can't change anything, but the names set the position.

3. All options judged together

Adding an option changes the gap between the others. Latency stays ~flat from 2 to 77 options.

4. The state is shared

Many questions per request: the state is billed once, and duplicate questions get bit-identical answers.

The bf16 trick: post-processing like a temperature would knock the numbers off the 16-bit grid. They're on it, so whatever calibration exists is in the weights.

Most of the judgement comes free with the open base. The clearest gain from Microsoft's training: picking 1 of many.

Decision-1's base model is public, so we can isolate what Microsoft's training added: run the untrained base the same way (sorted options, one pass, read the option scores) and compare.

On contract compliance (3 options) the two are indistinguishable: exactly 815 of 1,100 right each (0.7409), but they agree on only 81% of items, so each gets ~95 items right that the other misses; the identical score is partly coincidence. With names only, the untrained base is ahead (0.647 vs. 0.619), and a different prompt layout lifts it to 0.767–0.775. On 77 banking intents, training adds 12 points, and it carries over to MInDS-14 (+5.7) and ATIS (+8.8), which nobody tuned on.

Things training did not add: better contract judgement, and robustness to rewording the question (6.7% vs. 2.7% of decisions flipped; small sample).

Can you trust its confidence?

Bar = how often it was right · black line = how sure it said it was · honest when they line up. Gap: lower is better.

Microsoft's training fixed the confidence on routing, not on contracts. The fix: test on a few hundred labelled examples of your task and, if it's overconfident, soften its scores by one fixed factor. Its picks never change.

Why this matters: the whole point of a probability is to automate when it's sure and escalate when it isn't. That only works if "94% sure" really means right about 94% of the time.

How to read it: each row is a group of answers. The black line is the average confidence Decision-1 reported for that group; the bar is how often that group was actually right. BANKING77: they line up. ACE: when it says ~94%, it's right only 72% of the time.

Group sizes: BANKING77 521 / 539 / 1,470 answers; ACE (with option descriptions) 324 / 199 / 319 answers. Bins: 70–90%, 90–97%, 97–100% stated confidence. Computed from our raw Decision-1 test predictions.

Base vs. Decision-1 rows: "average gap" is the expected calibration error (ECE) from the job summaries. BANKING77: untrained Qwen3.5-9B 0.097 vs. Decision-1 0.015, so Microsoft's training removed most of the overconfidence. ACE: 0.106 vs. 0.106; same size of gap, but not the same model behaviour (they disagree on 19% of answers, and the base is slightly less overconfident by temperature: 1.33 vs. 1.65). We only have per-group numbers for Decision-1; the base model's raw predictions are on Azure ML storage we can't reach from here.

On ACE, the softening turned "says 97%, right 82%" into "says 94.5%, right 91%" (answers stated at ≥90%).

The fix, if asked how: it's called temperature scaling. Take the log of each returned probability, divide by one number T, and re-normalise. T is chosen on labelled examples (we used the 720 ACE calibration items, separate from test) so that stated confidence best matches accuracy. For ACE, T = 1.65. Real example: Decision-1 said Non-Compliant 92.4% / Compliant 6.7%; after softening, 79.1% / 16.1%. Same pick (it was actually wrong; the answer was Compliant), less certain. On the ACE test set, answers stated at ≥90% went from "says 97%, right 82%" to "says 94.5%, right 91%". Top choice unchanged on all 1,100 items, so accuracy doesn't move.

Simpler alternative: skip the softening and pick your automation threshold from labelled data. On raw ACE scores, automating only above 97% keeps 29% of cases at 89% accuracy.

Other T values: BANKING77 1.02 (untrained base 1.41); ACE 2.75 without option descriptions; ContractNLI 1.60; unseen intent sets ≈ 0.7 (slightly underconfident).

Can we rebuild it?

Mostly, except what Microsoft's training adds

Interface: yes

Sort, one-pass scoring, shared state, all on the open base with no training.

Contract judgement: yes

The base already matches it; our fine-tunes match or beat it.

Many options: no

Still 12–14 points behind on BANKING77 after more data, synthetic data, 5× training and RL.

Unknown: how it was trained. Jev's docs mention RL for calibration, which is our next experiment.

The many-options skill is the moat. Everything else is engineering you can copy.

Takeaways

If you use one tomorrow

Write option descriptions

+12 points on ACE (0.619 → 0.741). They're read in full.

Check calibration on your data

Trust it on routing; recalibrate on compliance-style tasks.

Name options deliberately

They're sorted by name, so names decide position.

Have labels? Try a classifier first

Embeddings + logistic regression: 0.944 on BANKING77 at $0.002 per 1k decisions.

A decision model is an LLM that isn't allowed to talk: one pass, one score per option, and training that makes the probabilities mean something.

Close on the one-liner, then questions.
