The thesis

Maybe we optimized for the wrong output

What software needs

route = "fraud" risk = 0.82 approve = false

Values that software can branch on.

What an LLM naturally produces

"Based on the available information, this appears most likely to be a fraud-related request because..."

Language that we then convert back into software state.

We trained models to communicate with humans. But many software decisions don't require language at all.
The Jev thesis 4
Why this matters

LLMs are surprisingly expensive decision engines

Typical LLM path

State ↓ Prompt ↓ LLM ↓ token → token → token → token ↓ JSON / text ↓ parse ↓ decision

Decision-model path

State ↓ Decision model ↓ P(A), P(B), P(C) ↓ policy ↓ action

If the answer space is already known, generating language may simply be unnecessary computation.

Calibration 7
One important caveat

“Cannot hallucinate” ≠ “cannot be wrong”

Bounded output solves

  • Invalid output types
  • Invented categories
  • Unexpected prose
  • Parsing failures

It does not solve

  • Wrong classification
  • Missing domain knowledge
  • Distribution shift
  • Badly specified choices
  • Misleading confidence

A decision model can return a perfectly valid but completely wrong value.

9 Oct 2026 · Microsoft Foundry

Microsoft-Decision-1

What it is

  • Decision scoring for routing, classification, prioritisation, verification, workflow control
  • No prose: state + fixed options in, calibrated probability per option out
  • Post-trained Qwen3.5-9B for single-pass scoring; to be rebased on MAI and OpenAI models
  • Microsoft Foundry and OpenRouter · $0.042 per 1M input tokens, output free

Same programming model as Jev

POST …/microsoft/v1/systemone { "state": "API returns 500", "questions": { "team": { "type": "choice", "criteria": { "billing": "...", "engineering": "..." }}}}

noul (true?) · choice (which?) · score (how much?)

Microsoft's claims

  • Best accuracy across 36 benchmarks (~150k questions, blind from training)
  • P50 2.5× faster than H2O-Lightning-4B, ~35× faster than GPT-6 Sol
  • Flips on 1.3% of perturbed inputs; none when options are reordered
  • Xbox Research labelling: ~GPT-6 Sol quality, 14× faster, 200× cheaper
Note the recipe: a post-trained open 9B base model behind a Jev-style API (even the word "noul"). Not a giant new model; a trained decision readout. We benchmark it as B1 in Part 1.

Sources: Microsoft Command Line blog "Microsoft-Decision-1: Our model for fast decision-making" (9 Oct 2026); Microsoft Learn "Deploy and use Microsoft-Decision-1 in Microsoft Foundry". Benchmarks are Microsoft's own.

Possibility #4

Maybe the options are evaluated jointly

Independent scoring

score(A) = F(state, A) score(B) = F(state, B) score(C) = F(state, C)

A never “sees” B or C.

Listwise scoring

scores = F( state, question, [A, B, C] ) → [.54, .09, .37]

The alternatives themselves become part of the context.

The question becomes less: “How similar is A to the state?” and more: “Given these competing alternatives, how should probability mass be distributed?”

Reported option-set and option-order effects in independent Jev probing are consistent with this kind of interaction — although they do not prove a specific architecture.

Maybe language generation is just one readout

Normal foundation model

Decision mode

The unresolved question

Where does the real advantage come from?

Hypothesis A — new readout

Foundation model ↓ rich representation ↓ decision head ↓ probabilities

Most of the benefit comes from avoiding autoregressive generation.

OpenAI Decisions v1 points in this direction.

Hypothesis B — new representation

specialized decision training ↓ different representation ↓ better calibrated decisions

Specialized training changes what the model learns internally.

Jev's RLCD thesis points in this direction.

How much value comes from the model, and how much comes from the readout?

Part 2 · Open model
Part 2 · Same model, nine ways to ask

The readouts we built

C1 · Generate baseline

Think, write the label, parse it.

prompt → reasoning → "Non-Compliant" → parse → one-hot

C2 / C3 · Score each label

Force every label as the answer, compare likelihoods. C3 encodes the state once and branches the KV cache.

P("Compliant") P("Non-Compliant") P("Not-Applicable") → softmax

C4 · Yes/No per candidate

Cross-encoder: "is this the right decision?", one option at a time.

(state, A) → Yes/No (state, B) → Yes/No (state, C) → Yes/No → softmax

C6 · List options, read one token

All options in the prompt, ONE forward pass, read the letter distribution.

[A] Compliant [B] Non-Compliant [C] N/A → P(A) P(B) P(C)

C2+ / C6+ · Debiased

Average over option orders; subtract the model's prior from a content-free input.

mean over orders − prior("N/A")

C8 · Reason, then read

Let it think, then read P(A..C) at the answer instead of sampling.

prompt → reasoning → read P(A) P(B) P(C)

C9 · Cascade

Fast readout first; escalate to reasoning only when unsure.

C6+ → max P ≥ t ? answer : C8

C5 · Listwise head trained

Hidden state of each listed option → one shared linear scorer. Base model frozen.

h(option k) at layer 16 → w·h → softmax

C7 · Early-exit head trained

Run only 16–20 of 24 layers; linear head on the answer position.

layers 1..16 → h(answer) → W·h → softmax

Maps to the possibilities: cross-encoder (#2) = C4 · shared state (#3) = C3 · listwise (#4) = C5/C6. "Trained" = a linear layer fit on the dataset's train labels (2k–6k examples); everything else is zero-shot. Diagrams per method: docs/methods.md

Part 2 · Finding 5
Back to the core question

Model or readout? Our evidence says: both, but differently

For "it's mostly a new readout"

  • Part 2 One forward pass gives speed, valid outputs and usable probabilities (BANKING77)
  • Part 2 The answer already lives in mid-layer activations (C7 at layer 16)
  • Part 2 Sharing the encoded state across options changes nothing (C3 = C2)
  • Context OpenAI reportedly built Decisions v1 on existing Luna weights in about a week

For "the training matters"

  • Part 2 Untrained readouts carry strong format-specific biases (ACE)
  • Part 2 A tiny trained head fixes that: 0.47 → 0.93 on the same activations
  • Part 1 Decision-1 is calibrated out of the box; prompted GPT-6 Luna is not
  • Part 2 Deliberative questions still need reasoning somewhere

Our current read: a strong base model plus a trained decision readout. The training seems to matter less for what the model knows and more for how it answers and how honest its confidence is.

A hypothesis, not a measured comparison: Parts 1 and 2 use different models. Jev and Decision-1 internals are not public.

Caveats and what's next

Caveats

  • Parts 1 and 2 use different models and infrastructure: don't rank across them
  • ACE test differs from its train data (labels look LLM-filtered; scenario text leaks the label)
  • Trained heads/classifiers use labels, zero-shot methods don't; compare within each group
  • Part 2 latency/cost: one A100, batch 1, no serving engine (upper bounds)
  • Our debiasing prior N/A collides with ACE's Not-Applicable; needs a rerun
  • One run per configuration

Next

  • A harder, more ambiguous dataset (legal clauses, contract NLI, privacy norms)
  • OpenAI Decisions API vs. GPT-6 Luna: the same-model test for Part 1, once available on Azure
  • Part 2: train the readout without target labels (a small LoRA "decision fine-tune", in the spirit of Tev1 / RLCD)
  • Fix the neutral prior; try a C6 → C8 cascade
  • Multiple questions over one shared encoded state

Caveats
Discussion

Questions I'd leave us with

1. Are decision models a new model class, or a trained readout on top of foundation models? Our data: the answer already sits in mid-layer activations.
2. Is calibration the real innovation? In both parts, generating the answer is always "100% sure"; the decision API and the probability readouts know when they don't know.
3. How do we tell, before deploying, whether a decision is "System One" (read it in one pass) or needs deliberation (reason first, or cascade)?
4. With a few thousand labels, a simple trained layer (on embeddings, or on the open model's activations) tops its part on both datasets. When is a general-purpose, zero-shot decision model worth it?
Discussion 21
Takeaway

Maybe the model doesn't always need to talk.

state ↓ bounded question ↓ probability distribution ↓ policy ↓ action

Jev made the idea explicit. OpenAI's rapid response suggests the pattern may be broader than one model, one architecture, or one vendor.

Our experiments agree: the decision is often already inside the model. The hard part is reading it out honestly, and knowing when it needs to think first.
